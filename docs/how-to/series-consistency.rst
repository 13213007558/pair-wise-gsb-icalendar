==================================
Check recurring series consistency
==================================

An iCalendar file can parse without errors and still contain a recurring
series that cannot be used: the master component and its exceptions are
defined in separate ``VEVENT``/``VTODO``/``VJOURNAL`` components, so each one
can look valid while they disagree with each other. For example, the master
may use an all-day ``DATE`` ``DTSTART`` while an exception claims a
time-zoned ``DATE-TIME`` ``RECURRENCE-ID``.

Use :func:`~icalendar.check_series_consistency` (or
:meth:`Calendar.check_series_consistency
<icalendar.Calendar.check_series_consistency>`) to run this check explicitly.
It collects every error it can determine without expanding the recurrence
set (infinite series are safe) and without modifying the calendar: it never
rewrites dates, invents ``UID`` values, or removes exceptions. Whether a
``RECURRENCE-ID`` actually names an instance generated by the master is not
checked.

Run the check
-------------

.. code-block:: pycon

    >>> from icalendar import Calendar, check_series_consistency
    >>> calendar = Calendar.example()
    >>> report = check_series_consistency(calendar)
    >>> report.ok
    True

Raw iCalendar data (``str``, ``bytes`` or a :class:`~pathlib.Path`) is read
leniently for the check, so existing parse errors are included in the report
instead of stopping it. This does not change
:meth:`Calendar.from_ical <icalendar.Calendar.from_ical>`.

Read the report
---------------

Each :class:`~icalendar.SeriesConsistencyError` has a stable error ``code``,
the series ``uid``, the ``component_index`` (counting only ``VEVENT``,
``VTODO`` and ``VJOURNAL`` components in document order, starting at 0), and a
``property_path`` inside the component, such as ``RRULE[1].UNTIL``.

.. code-block:: pycon

    >>> for error in report:
    ...     print(error.code, error.uid, error.component_index, error.path)

To fail explicitly, call :meth:`SeriesConsistencyReport.raise_if_errors
<icalendar.SeriesConsistencyReport.raise_if_errors>`, which raises
:class:`~icalendar.SeriesConsistencyErrorFound`.

What is checked
---------------

- one unique master component (without ``RECURRENCE-ID``) per ``UID``;
- no two exceptions claiming the same ``RECURRENCE-ID`` -- the modified
  ``DTSTART`` of an exception never changes its identity;
- ``RECURRENCE-ID`` value type (``DATE``/``DATE-TIME``) and time form
  (UTC, time-zoned, floating) matching the master ``DTSTART``;
- ``RRULE`` ``COUNT``/``UNTIL`` exclusivity and the ``UNTIL``/``DTSTART``
  value type and time form requirements;
- ``DTEND``/``DURATION`` (or ``DUE``/``DURATION``) exclusivity, all-day
  duration units, negative durations, and end values earlier than the start;
- ``RDATE``/``EXDATE`` value type and time form compatibility with the series;
- conflicting ``RANGE=THISANDFUTURE`` declarations on overlapping original
  instances;
- parse errors already recorded for the input components.

Unknown ``X-`` properties are left untouched.
